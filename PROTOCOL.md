# Preregistered code-judge order diagnostic

2026-11-17, before measured inference. New local diagnostic inspired by position-swap evaluation, not an MT-Bench replication, human-preference study or evaluation of frontier judges. Hypothesis: a judge may change its substantive decision when the same two candidate implementations trade A/B positions. An order-consistent decision may also be wrong. The study differs from the earlier AI-review-versus-tests pilot: implementations are fixed, no repair agent receives feedback, and only presentation order varies in the primary pairs.

## Data and design

Eight authored Python programming contracts, each with a known valid implementation, a deliberately flawed implementation, an independently expressed valid alternative and fixed execution tests. Candidate bodies have no comments instructing the judge. Test fixture code is owned authored material, not model output or downloaded code. The complete candidate programs execute only in oracle preparation/auditing, never as model actions. The local judges do not receive test cases, expected outputs, gold labels, file names, model provenance or the valid alternative unless it is part of a tie control.

Main cases: 8 tasks × 2 orders × 2 installed models = 32 calls. Canonical order puts the valid implementation in A and the buggy one in B; reversed order swaps the exact strings. Positive/negative judge controls: 8 additional cases per model, tasks 0–3 pair the two valid alternatives and tasks 4–7 pair the identical buggy implementation with itself. Under the stated binary contract rubric, both controls require TIE. Total 48 model calls, 24 per model. These are finite diagnostic examples, not random samples or eight independent production trials. Main pairs use the same task and one fixed seed, no decoding repetitions. Four correct/correct and four incorrect/incorrect controls test TIE behavior, not open-ended preference quality.

## Judge and frozen settings

Qwen2.5 7B and Qwen3 8B from existing Ollama installations; pin complete installed digests before measurement. Use the exact saved system/user messages in request.py, one chat per call without history. Ask for A if only A satisfies the contract, B if only B does, TIE if both or neither does. Judge code as data, do not execute it, provide JSON {winner:A|B|TIE, reason:string}. Apply the same JSON-schema decoding to both models and orders; this is not a schema-decoding comparison. No chain-of-thought requirement, repair, extra reference answer or model feedback. `think:false`, temperature 0, seed 20261117, num_ctx 8192, num_predict 192, keep_alive 5m, 90-second per-request timeout. Store all options and raw responses. One model resident at a time; shuffle the 24 cells within each model block with seed 20261117. Fixed block order Qwen2.5 then Qwen3. No model parallelism, downloads or extra spend. Do not compare latency: cold starts and model sizes are not controlled for speed.

## Execution oracle and strictness

Implement only evaluation.py through INVARIANT. `passes(code, task)` compiles/executes authored candidate code, calls solve(*args) on a deep copy for each case, and checks ordinary Python value equality against expected values. Expected exceptions match with isinstance, including valid subclasses (do not repeat the historical exact-class grading artifact). A normal result when an exception is expected, wrong value, wrong exception, syntax error or missing solve fails the candidate. No code supplied by a model is executed. Candidate fixtures must finish promptly; no generic arbitrary-code sandbox claim. `gold(case,tasks)` returns A/B if exactly one option passes, else TIE. Independently verify all valid and alternative fixtures pass and every deliberate mutant fails before freezing model requests. The test oracle covers the written edge cases but is not a proof for arbitrary unseen implementations.

For tasks with preserve_inputs=True (dedup and merge), compare the argument copies before and after the call and reject mutation; those two contracts explicitly prohibit mutation. Other tasks have no additional mutation requirement.

`score(text, expected)` accepts only a JSON object with exactly keys winner/reason, winner one of A/B/TIE and a string reason. Invalid JSON, wrong/missing/extra fields, bool values or unsupported labels produce schema_valid=False, winner=None, correct=False, without repaired parsing. Valid outputs retain the winner and correct=(winner==expected). Rationale is preserved for inspection, not graded for logical faithfulness.

`summarize(records)` takes the 24 scored records for one model: 16 main records and 8 controls. Each record has case_id, task_id, kind, order and score (the three fields returned by score). Require unique case_id and exactly eight task groups, each with canonical/reversed main records and one control; require four both_valid and four both_buggy controls and reject other kinds/orders. Report schema_valid/24; main_correct/16; correct_when_valid_first/8 and correct_when_valid_second/8; control_correct/8, split both_valid/4 and both_buggy/4. For each main task normalize canonical A/reversed B to candidate `valid`, canonical B/reversed A to `buggy`, and TIE to `tie`. Report consistent_pair/8 (same non-null normalized choice in both orders), changed_pair/8 (two valid but different normalized choices), invalid_pair/8, both_correct_pair/8, consistent_wrong_pair/8 (both choose the buggy candidate), persistent_tie_pair/8, always_A_pair/8 and always_B_pair/8. Pair categories consistent/changed/invalid must exhaust all eight tasks; always-A/B are positional diagnostics, not labels proving a stable population bias. Missing/duplicate cell or malformed schedule blocks aggregation. Return raw integer numerator fields only, plus total_calls=24, main_calls=16, control_calls=8 and pairs=8; all metric field names are exactly the names given here.

## Acceptance, measurement and validation

Eight protected checks cover valid/buggy/alternative execution, exception subclass acceptance, main/control gold labels, strict JSON scoring, swapped-choice normalization, correct/incorrect/tie versus positional persistence, and incomplete/duplicate records. Check scorer with positive, negative and malformed controls before any primary model calls. Freeze protocol, fixtures, order, schema, request builder, implementation, tests, runner, auditor and model manifests, and commit them before the single primary run. Record issuance before each request; preserve every request, response, timestamp, schema/quality result and token count. Do not retry an uncertain or failed model request, tune fixtures from observations, drop cells or silently change options. A transport/model/metadata error leaves an incomplete diagnostic. Cap/truncation is retained and prevents a publication-ready comparative claim until explicitly assessed; do not raise the cap mid-run. Incorrect judgments and ties are valid observations, not grounds for a rerun.

An independent auditor imports neither evaluation.py, request.py nor run.py. It reconstructs gold by executing the authored programs against the fixed tests, reconstructs every prompt and permutation, checks all hashes/installed digests/settings, verifies all 48 distinct terminal responses and issued files, re-parses JSON and recomputes all marginal and paired metrics. An image, if useful, contains only measured metric/condition labels and numerators/denominators. Interpretation must distinguish order sensitivity from a statistical estimate of position bias, and consistency from correctness. Null results are publishable with scope limits. No human-preference, model ranking, overall software-review or production reliability conclusion.
